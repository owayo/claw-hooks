# AGENTS.md - AI Agent Instructions

Instructions for AI coding agents (Claude Code, Cursor, Windsurf, Codex, Grok, GitHub Copilot, etc.)

## Project Overview

**claw-hooks** - Hooks CLI for AI coding agents with TOML-based configuration.

- **Language**: Rust (MSRV 1.85)
- **Version**: 26.8.100
- **Purpose**: Block dangerous commands, run formatters/linters only after file save/edit completes, send notifications on agent stop/subagent events
- **Supported Agents**: Claude Code, Cursor, Windsurf, Antigravity CLI, Codex CLI, Grok CLI

## Key Features

1. **Command Blocking**: `rm`/`kill`/`dd` → suggest `safe-rm`/`safe-kill`. The command filters apply to every shell tool, not just `Bash`: Claude Code's `PowerShell` tool carries the same `tool_input.command` shape, and on Windows without Git Bash it becomes the *only* shell tool (the official spec states Claude Code "doesn't register the Bash tool at all" there and that "a hook that matches only `Bash` never fires"). `HookInput::is_shell_tool()` therefore matches `Bash | PowerShell`, and the `rm`/`kill` blocklists additionally carry the canonical PowerShell cmdlet names (`remove-item`, `stop-process`) plus the cmd/PowerShell alias `rd` and `Stop-Process`'s other built-in alias `spps`; the familiar aliases `rm`/`rmdir`/`del`/`erase`/`kill` are already covered by name. PowerShell assigns exactly two default aliases to `Stop-Process` — `kill` and `spps` — so omitting the latter let a fully equivalent call through under a different spelling (`spps -Name node`), which is why it is listed even though `rm`'s alias set was already complete. The short alias `ri` is deliberately **not** blocked because it collides with Ruby's `ri` documentation tool. Configure Claude Code with `"matcher": "Bash|PowerShell"` so the hook fires for both.
2. **AST Parsing**: tree-sitter-bash for accurate command detection (optional feature `ast-parser`), with command basename/executable-extension/case normalization (`/bin/rm`, `RM.EXE`), shell quote-removal handling (`r\m`, `r''m`, `$'r\x6d'`), and fallback parsing that also handles subshells/command substitutions/env-prefix commands, single `&` (background), newline separators, `eval`, `find -exec`/`-execdir`, `xargs -I`/`xargs sh -c`, Windows `cmd /c`, and wrapper options (e.g., `sudo -n`, `/usr/bin/sudo -u root rm`, `sudo --user root`, `sudo VAR=value rm`, `timeout --signal TERM 10 rm`, `command rm`, `exec rm`), value-taking flags followed by numeric arguments (`xargs -n 1 rm`, `sudo -u 1000 rm`, `nice -n 10 rm` — the numeric token is preserved so the flag does not swallow the real command), `bash -c --` option terminators, shell `-c` clustered with inline script (`bash -c'rm -rf /'`, `bash -lc'rm -rf /'` — shells join `-c` and the immediately-quoted script into a single argv token `-crm -rf /`; the parser splits the script out of the cluster so the inner command is still detected and cannot bypass the filter), and `env -S` / `--split-string` command strings (env-specific, so `sort -S` etc. are not misparsed), command-position brace expansion (`{rm,-rf,/p}`, `/bin/{rm,ls}`, `{r,}m` → first-choice expansion so the launched command is still detected), brace command groups (`{ rm -rf /; }` — the leading `{` group delimiter is skipped so the inner command is still detected, including in the fallback parser), shell control structures in the fallback parser (`if … then rm …`, `for/select … do rm …`, `while/until … do rm …`, `case W in P) rm …`, `! rm …` — the control keywords, loop variables, and `case` patterns are skipped so the inner command is still detected; loop variables and patterns named like a blocked command, e.g. `for rm in …` or `case x in rm) …`, are NOT misdetected as that command; command substitutions inside loop/case headers such as `for f in $(rm …)` are also extracted, preventing the fallback parser from failing open on control-flow-wrapped dangerous commands), process substitution (`diff <(rm ...) <(ls)`, `tee >(rm ...)` — the inner command actually runs, so it is extracted; bare redirections `< file` / `> file` are not misdetected), and additional execution-delegation wrappers (`setsid`, `stdbuf`, `taskset` mask, `nsenter`, `unshare`, `setpriv`, `chroot`/`flock` with their leading directory/lockfile positional, `busybox`/`toybox` applets, `su`/`runuser`/`flock -c` shell-string re-evaluation, `pkexec` (Polkit), `gosu` (container-friendly setuid wrapper that takes a leading `<user[:group]>` positional and runs the rest as that user), and Busybox/Alpine-style `su <user> cmd` (`su` takes a leading positional username followed by the command, distinct from `su -c "cmd"` which is handled via the shell-`-c` path; the parser also recognises GNU/util-linux `su` value-taking flags such as `-c`/`-g`/`-G`/`-s` and `--shell`/`--command`/`--group`/`--supp-group`/`--session-command` so `su -s /bin/bash root rm` does not consume `/bin/bash` as the user positional and misdetect the real command) — all expanded so `pkexec rm -rf /` / `gosu root rm -rf /` / `su root rm -rf /` cannot bypass the filter under elevated privileges). For wrappers that take a leading positional (`su`/`gosu`/`chroot`/`flock`), the `--` option terminator still leaves that positional in place, so the parser consumes the remaining leading positionals after `--` before locating the executed command (`su -- root rm -rf /` / `gosu -- root rm -rf /` resolve to `rm`, not the username `root`); a bare `sudo -- rm` keeps returning the token after `--` since `sudo` has no leading positional. Wrapper chains (`sudo sudo … rm`) are expanded iteratively rather than recursively so even a very long chain (within the size limit) cannot overflow the stack and fail open. When a wrapper's resolved command is itself a re-evaluating command (`eval`, `xargs`, `find -exec`/`-execdir`, `env -S`, or a shell `-c`), the inner command string is extracted and re-parsed through a shared helper used by both the top-level and wrapper-expansion paths, so `sudo eval 'rm -rf /'` / `sudo xargs rm` / `sudo find . -exec rm {} \;` / `timeout 10 env -S 'rm -rf /'` are detected rather than failing open (previously the wrapper-expansion path re-evaluated only the shell `-c` form and let the others through); the extraction is applied only to genuine re-evaluating commands via their argument helpers (not by blindly re-joining the tail), so a quoted argument to a non-re-evaluating command — e.g. `sudo echo '; rm -rf /'` or `sudo find . -name rm` — stays an argument and is not over-blocked. The custom-filter command-string extractor uses the same top-level terminator splitter (`;`, newline, single `&`) as the AST/fallback dangerous-command path, so anchored regex filters (`^rm `) cannot be evaded by chaining the target command after a newline or `&` (e.g., `echo ok\nrm -rf /tmp`, `echo ok & rm -rf /tmp`). Three further execution-delegation wrappers are recognised: **`arch`** (macOS `/usr/bin/arch`, which runs the following command under a selected architecture — `arch -arm64 rm -rf /` was previously a complete bypass on the project's primary platform; the Linux coreutils `arch` merely prints the machine name and ignores its arguments, so recognising it there over-blocks a no-op command, which the fail-closed policy prefers over a missed detection), **`systemd-run`** (runs the command as a transient unit and can delegate privileges via `--uid`/`--machine`, same rationale as `pkexec`/`gosu`), and **`script`** (allocates a pty and runs the command — BSD/macOS uses the `script [file] cmd …` positional form, so it takes one leading positional like `chroot`/`flock`, while util-linux uses `script -c "cmd"`, handled through the shared shell-`-c` path; `script` is therefore registered in both the wrapper list and `SHELL_COMMANDS`, exactly as `flock` already is). Supporting `arch` also required the wrapper flag table to understand **single-dash multi-character flags**: `-arch <name>` must be matched by exact string equality *before* the short-flag cluster interpretation (`-nu`), because splitting it into characters would match some unrelated single-letter flag and consume the real command as that flag's value. Optional-argument flags stay boolean per the existing policy (util-linux's `--timing[=file]`), so they never swallow the command that follows — but `script`'s own table was corrected against the macOS synopsis `script [-aeFkqr] [-t time] [file [command ...]]`: **`-t` takes a value and `-F` does not**. The table had these reversed, and combined with `script`'s leading output-file positional that erased the real command twice over (`script -F /tmp/p rm -rf /` let `-F` eat `/tmp/p` and then consumed `rm` as the filename; `script -t 0 /dev/null rm -rf /` consumed `0` as the filename and read `/dev/null` as the command).

   The AST argument walk enumerates **every** node kind tree-sitter-bash can place in a command's argument position (`ansi_c_string`, `translated_string`, `command_substitution`, `process_substitution`, `arithmetic_expansion`, `brace_expression`, `test_operator` alongside the previously listed ones). A kind missing from that list drops out of the argument vector entirely and fails open in two distinct ways: the content itself disappears (`bash -c $'rm -rf /'` lost its `ansi_c_string`, so the shell-`-c` re-evaluation never ran), and the remaining arguments shift by one so a value-taking flag swallows the real command (`sudo -u $(id -un) rm -rf /` lost its `command_substitution`, letting `-u` consume `rm`). Relatedly, an expansion token can never be *confirmed* as a command name — its value is only known at runtime — so the wrapper walk skips `$(...)` / `$((...))` / `` `...` `` / `$VAR` and keeps looking for a concrete command (`timeout $((5)) rm -rf /` would otherwise stop at `$((5))`, which also fails `timeout`'s duration-token test). The fallback tokenizer tracks command-substitution and arithmetic-expansion nesting so the whitespace inside them no longer splits one word into several (`env -u $(echo FOO) rm` used to tokenize as `-u`, `$(echo`, `FOO)`, `rm` and lose `rm` the same way).

   Three more execution paths are covered: **`coproc`** (a bash ≥ 4 / zsh reserved word that runs the following command asynchronously, same class as `time`), **`trap`** (the handler string is re-evaluated by the shell on signal delivery, exactly like `eval`; `trap - EXIT` for removal and `trap '' EXIT` for ignore run nothing and stay allowed), and **here-strings / heredocs fed to a shell** (`bash <<< "rm -rf /"`, `sh <<EOF … EOF` — the body really executes but arrives as a redirect, so it appears in neither the argument vector nor the command children; heredocs attach to the enclosing `redirected_statement` rather than the `command` node, so both are inspected, and only when the receiving command is a shell — `cat <<EOF … EOF` stays plain text and is not misdetected; the fallback parser sees the `<<<` operator as a plain argument token instead, so it extracts the here-string through the shared re-evaluation helper). The fallback parser also skips **leading redirections** (`> file rm -rf /`, `2>&1 rm -rf /` — POSIX allows redirections before the command word, and treating the operator as the command name lost the real one), and no longer splits the `&` of an fd duplication (`2>&1`) as a background operator, which used to break the segment into `2>` and `1 rm -rf /` and misread `1` as the command.

   Five further fail-open paths were closed, all of them cases where a redirection or a control structure hid the real command from one of the two parsers. **Trailing redirections** (`env 2>/dev/null rm -rf /`, `sudo 2>/dev/null kill -9 1`) are the widest: tree-sitter-bash's `file_redirect` node claims *every* word after the operator as a `destination`, so the command that follows sinks into the redirect node and vanishes from the `command` node's argument vector as well — and because this is valid syntax, `has_error()` never fires and the fallback never runs. The parser now strips the redirect (the operator plus its first destination) and re-parses the remainder, the same "fold and re-analyse" technique already used for brace expansion; the removal only shortens the string, so the recursion terminates. The wrapper scan additionally skips redirection tokens outright, because `command_key("2>/dev/null")` resolves to `null`, which is neither a wrapper nor a re-evaluating command and therefore ended the walk. Redirections placed *before* the command word were already handled and are unaffected. The **`--` option terminator** ends option parsing only, yet the wrapper scan returned the very next token as the command — so `env -- FOO=1 rm -rf /` read `FOO=1` as the command and `timeout -- 5 rm -rf /` read `5`. It now records that options ended and keeps consuming the wrapper's non-option operands (env assignments, `timeout` durations, `taskset` masks, the leading positionals of `su`/`gosu`/`chroot`/`flock`), while treating a later `-`-prefixed token as a command name rather than a flag. **Control structures under a wrapper** (`time { rm -rf /; }`, `time if true; then rm -rf /; fi`, `time for i in 1; do rm -rf /; done`, `time case x in x) rm -rf /;; esac`) were known to the fallback's `parse_effective_command` but not to the wrapper scan, so the two implementations disagreed and the wrapper path returned `{` or `case` as the command; the skip rules are now a single shared `effective_command_index` that both call, extended to cover `(` and `function`. **here-strings and heredocs behind a wrapper** (`env bash <<< "rm -rf /"`, `sudo sh <<EOF … EOF`) were missed because the shell test ran against the node's own command word — `env`, not `bash`; `resolves_to_shell` now walks the wrapper chain iteratively to whatever command actually gets launched, and the `redirected_statement` branch passes the body's arguments so it can do the same. Finally, a tree whose `root_node().has_error()` is set is no longer trusted on its own: tree-sitter-bash returns `Some(tree)` for invalid syntax with nodes silently dropped (`bash 2>/dev/null <<< "rm -rf /"` loses its `herestring_redirect` to an `ERROR` node, so the here-string body is never analysed), so the string-based fallback is run alongside and the two result sets are merged. The AST walk also shifts off a leading control keyword when tree-sitter mis-parses `time if true; then rm …; fi` into a `command` whose name is `then` and whose arguments hold the real command — `has_error()` is not set there either, which is why the keyword skip has to run on the AST path too and not only in the fallback.
3. **Custom Filters**: Regex-based and argument-based command filtering. The command name is normalized through the same `command_key` helper the built-in filters use (basename, executable extension, case), so a `command = "npm"` filter also catches `/usr/bin/npm`, `./npm`, `NPM` and `npm.cmd` — previously only the built-in `rm`/`kill`/`dd` filters normalized, and a custom filter could be evaded by spelling the path out. Both the raw and the normalized form are tested, so a path-qualified pattern (`command = "/usr/bin/npm"`) keeps matching. Matching also runs against the **quote-removed** form of the command, i.e. the argv the shell actually builds. `strip_quoted_content` — which exists to stop `echo "yarn"` from counting as a `yarn` invocation — drops the *contents* of quotes along with the delimiters, so `npm "install" lodash`, `npm 'install' lodash` and `npm in\stall lodash` all collapsed to `npm  lodash` and slipped past an `args = ["install", …]` filter, even though every one of them runs `npm install lodash`. (The built-in `rm`/`kill`/`dd` filters only ever look at the command name, so they were never affected; a `sudo`-prefixed call happened to be caught because the wrapper-expansion path re-parses quote-removed arguments, which is what made the asymmetry visible.) Both forms are now tested, which closes the evasion while keeping the false-positive guard: patterns are anchored to the start of the command string, so a word that merely moves into argument position still does not match. That anchoring itself is applied as `^(?:…)` rather than `^…`, because alternation binds more loosely than the anchor — `command = "npm install|yarn add"` compiled to `(^npm install)|(yarn add)`, leaving the right-hand branch unanchored so that `git commit -m "fix yarn add"` was blocked. `with_args` wraps its `^…$` the same way.
4. **Extension Hooks**: Auto-format/lint on AfterFileEdit events only (not on BeforeCommand) for the file-editing tools `Write` / `Edit` / `MultiEdit` / `NotebookEdit` (the last one carries its path in `notebook_path` rather than `file_path`, so it is read through a fallback — without it every `.ipynb` edit silently skipped its formatter), with timeout support (`{file}` must appear exactly once, parent-directory traversal, shell redirection paths, tabs/newlines/NUL are blocked; on Windows, `cmd /c` shell metacharacters such as `%`, `!`, `^`, `"` are also rejected from file paths to prevent variable-expansion injection). Successful no-op formatter/linter notices are suppressed, while rewritten-file/failure output is preserved; agent-facing command labels contain only the configured program name.
5. **Stop Hooks**: Run commands on agent stop (lint/typecheck, notifications, git commit, cleanup). `report=true` hooks are waited on and failures are returned to the agent; `report=false` hooks are started detached with stdin/stdout/stderr discarded, and a background reaper thread `wait`s on each detached `Child` so the kernel does not accumulate zombie entries when Stop fires repeatedly. Loop prevention is three-layered: a cross-process env flag, the agent's `stop_hook_active` flag (Claude/Codex), and Cursor's `loop_count` (>= 1 means a follow-up was already fired, so all stop hooks are skipped — symmetric with `stop_hook_active`). Session-kind filtering: `agent_id` is documented as present "only when the hook fires inside a subagent call", and `agent_type` as present when the session uses `--agent` *or* the hook fires inside a subagent, so a `Stop` carrying both non-empty fields identifies a delegated session while a main session launched with `--agent` carries `agent_type` alone — `agent_type` by itself must therefore remain primary. Each `[[stop_hooks]]` entry has `session_scope = "primary" (default) | "delegated" | "all"`, and the default `primary` runs hooks (and the NanoBuddy stop notification) only for main-session Stops, so teammate fleets do not cause notification spam, redundant lints, or racing parallel git auto-commits. Missing/empty/blank/non-string discriminator fields are treated as primary (misclassifying a delegated session as primary only runs extra hooks, while the reverse would silently drop the final lint/commit, so the parse errs toward primary); in-process subagents (the Agent tool) fire only `SubagentStop`, not `Stop`, and are unaffected. **Agent-team teammates are in-process** (`SubagentStart` fires "each time an in-process agent team teammate handles a new message") and signal completion through the separate `TeammateIdle` event, which claw-hooks deliberately does not implement — see the Claude Code section for why.
6. **Subagent Events**: NanoBuddy notifications on subagent start/stop
7. **Output Normalization**: ANSI stripping (CSI/OSC/SS2/SS3, plus the general ECMA-48 escape form `ESC` + intermediate bytes `0x20–0x2F` + final byte `0x30–0x7E`, and bare `SO`/`SI` control bytes), carriage-return progress collapsing (a logical line rewritten in place via a lone `\r` — common in Godot headless import and download/migration progress bars — is reduced to the final post-`\r` segment that a terminal would actually display; Rust's `str::lines()` only splits on `\n`/`\r\n`, so without this the line would otherwise retain every intermediate progress state plus the literal `\r` control bytes, and `\r\n` Windows line endings are unaffected because they are already split into separate lines), path prefix removal including absolute paths under directories with spaces (the prefix is only stripped when both the preceding character and the following character match the path-boundary conditions used by `extract_absolute_paths` — line start / whitespace / `-` / `>` / `=` before, and a filename character after — so that a common prefix appearing incidentally inside non-path text such as `foo/proj/src/...` is not silently mangled), repeated decorative character compression (`.`, `=`, `-`, `─`, `━`, `^`, `·`, `→`, `_`) — the `_` rule collapses rustc/ruff/biome multiline span underlines (`| |_______^` → `| |_^`) while snake_case separators (1–2 underscores) are preserved — plus trailing progress ellipsis compression and rustc-style location marker compression (`-->` / `---->` → `->`, single-hyphen `->` preserved so function return types stay intact), space-separated decorative run compression for biome diff visualization (`→ → → → → → → Google` → `→ Google`, applies to `·` and `→` with single-space delimiter), biome duplicate diff context line-number compression (`129 129 │ text` → `129 │ text`, empty context lines `129 129 │` → `129 │` when both line numbers are identical integers; differing pairs like `10 9 │` are preserved as informative), diagnostic frame-line removal (lines composed solely of `|` / `^` / `_` / Box Drawing characters (U+2500–U+257F: `│`, `─`, `╭─╮` / `╰─╯` banner frames from pnpm-style update notices, biome `─────` separators) and whitespace — ruff/biome/rustc caret and separator scaffolding — are dropped entirely, since the pointed-at column already appears numerically in the preceding `file:line:col` header; lines with any alphanumeric content such as headings, source lines, labelled carets `| ^ expected u32`, banner body lines `│ Update available! │`, or snake_case-containing lines like `__init__` are preserved — `_` is in the dropped set so rustc/clippy multiline span underlines collapsed to `| |_^` are removed, but any letter/digit keeps the line), progress-prefix line collapsing limited to a whitelist of progress words (`Compiling`, `Checking`, `Building`, `Blocking` — cargo's repeated `Blocking waiting for file lock on ...` lines — etc.) where a run of consecutive lines each starting with any whitelisted progress word is collapsed as one run even when the words differ (cargo's concurrent build interleaves `Compiling`/`Checking`, so a same-word-only rule would leave most progress noise uncollapsed) — single-word runs summarize as `... (and N more lines starting with "<word>")`, mixed-word runs as `... (and N more progress lines)`, while diagnostic lines (`error:` / `warning:`) break the run and are never collapsed so their per-line information is preserved, lint ruleset-incompatibility configuration warnings (ruff's `warning: … are incompatible. Ignoring …` lines emitted on every run — about the D-rule set rather than the edited code) are dropped as pure per-edit noise while genuine code diagnostics such as `warning: unused variable` are preserved, successful no-op formatter/linter notices (`All checks passed!`, `N file(s) already formatted/left unchanged`, Biome `No fixes applied`) are removed only when the command succeeds, per-diagnostic verbatim source-excerpt deduplication (biome re-prints the same code excerpt once per sub-block of a single diagnostic — the `!` message, the `i` note, and the `i Safe fix:` block — and ruff re-prints context lines inside its fix diff, so a line-numbered excerpt line such as `3 │ let c = 3;` / `> 3 │ let c = 3;` / `12 | x = 1` that repeats verbatim within one diagnostic is dropped after the first occurrence; diff lines `3 │ - old` / `3 │ + new` and ruff's `- old` / `5 + new` are preserved because they are the fix itself, and the dedup scope resets at each diagnostic header — a line ending in `━` for biome, or starting with `-> ` for ruff/rustc/clippy — so a different diagnostic keeps its own copy of the same source line as position information; measured on real output this removes ~6% of ruff and ~14% of biome bytes), cross-diagnostic duplicate excerpt-block removal (ruff and biome re-print the *entire* source excerpt for every diagnostic that points at the same place — one function definition draws `ANN201` / `D103` / `ANN001` / `ANN001`, one `let` draws `useConst` / `noUnusedVariables` — so when a diagnostic's leading run of context lines is byte-identical to the *immediately preceding* diagnostic's, the whole run is dropped; the location survives in each diagnostic's own header, the comparison is always against the previous diagnostic's original excerpt so a chain of three or more collapses to one copy while a diagnostic separated by a different excerpt keeps its own, and diff lines are excluded from the block by `is_source_context_line` so the actual fix is never lost — measured on real output this removes a further ~15% of ruff and ~8% of biome bytes on top of the per-diagnostic dedup, which matters because the default 1000-character truncation was otherwise spending its budget on repeated code instead of on the diagnostics that follow), removal of tool summary lines that are redundant *only when diagnostics accompany them* (biome's `Checked N file(s) in <duration>. No fixes applied.` counter and its closing `check ━` / `× Some errors were emitted while running checks.` block — both restate what the listed diagnostics already prove; when such a line is the entire output it is kept, because then it is the only signal that nothing was wrong, and suppressing that case is the caller's success-gated no-op check instead — this split is what keeps a failing command from losing its sole output line), and character-count-based output length truncation for token efficiency.

   Two ordering rules matter here. First, `ESC` + intermediate-byte sequences must be stripped: terminfo's `sgr0` is `\E(B\E[m` (and `\E[m\017` under some `TERM` values), so consuming only one byte after `ESC` leaks the final byte into the text and turns a rustfmt diff line into `B+ assert!(`. That single stray character defeats every downstream rule — diff-line, source-context and frame-line detection all stop matching — so colored `cargo fmt --check` output was previously left almost entirely uncompressed. Second, the success-time no-op check (`is_noop_success_output`) runs on the **normalized** string, not the raw one, and an output that normalizes to empty counts as a no-op. `ruff check --select D…` prints `All checks passed!` on stdout while writing its ruleset-incompatibility warnings to stderr on every run; judging the raw concatenation marked it "not a no-op", and normalization then deleted only the warnings, so `[ruff] All checks passed!` was returned to the agent after roughly a quarter of all file edits.

   Two further correctness rules govern what the compressor may touch. **OSC sequences are scanned with `peek`, not `next`.** Consuming the terminator eagerly swallowed the `ESC` that starts the *next* sequence, so a title-setting `ESC ] 0 ; …` immediately followed by a color code leaked a literal `[31m` into the body — and that stray text defeats every rule below it, exactly like the `sgr0` case above. An unterminated OSC also now stops at any C0 control byte other than BEL, matching real terminals; without that, a single truncated hyperlink swallowed the entire remaining output and the agent saw a clean lint run. **Decorative-run compression no longer touches the code body of a source-excerpt line.** `collapse_repeated_chars` runs on whole lines, so its `-->` rule (position-independent) rewrote the comment terminator in every `<!-- … -->` a linter re-printed, and its four-or-more `_` rule rewrote identifiers: measured examples include `3 │ <!-- TODO: fix -->` → `<!-- TODO: fix ->`, `4 │ MY____CONST = 1` → `MY_CONST = 1`, and `5 │ | --- | ---- |` → `| --- | - |`. The agent then writes a fix against a nonexistent identifier or syntactically broken markup. The line is now split at the `│`/`|` separator — compression applies to the line-number side only, which never contains decorative runs, so nothing is lost. rustc's own multi-line span underline (`| |_______^`) has no line number before the separator and therefore still compresses.

   That line-number guard is necessary but not sufficient, because **unified diff output carries no line numbers at all**. `rustfmt --check` / `cargo fmt --check` / `ruff format --diff` emit plain `-old` / `+new` lines, which `source_line_body_offset` cannot recognise and therefore cannot protect, so the two position-independent rules went on rewriting code inside them: `-const MY____CONST: u32=1;` became `-const MY_CONST: u32=1;` (four-or-more `_`), and `// tag <!-- note --> end` became `<!-- note ->` (the `-->` rule). Both now carry a context test instead of relying on the caller to pre-filter the line — a `_` run adjacent to an alphanumeric character is part of an identifier and is left alone, and `-->` collapses only when nothing but whitespace precedes it on the line, which is exactly where rustc and clippy put their location markers. Runs of four or more hyphens still compress everywhere, so `text ----> end` is unaffected. Two further additions on the compression side: biome's `format` subcommand reports `Formatted N file(s) in <duration>. No fixes applied.`, the same shape as the `check` subcommand's `Checked …` line but with a different verb — only `Checked ` was hardcoded, so roughly one edit in four returned that single content-free line to the agent; and cross-diagnostic excerpt removal now also drops a **partially** overlapping window. Linters print a few lines of context around each finding, so consecutive diagnostics pointing at nearby lines produce excerpts that slide over one another (`6,7,8,9` followed by `7,8,9,10,11`); comparing whole blocks for equality missed every one of these, and the leading run that the previous diagnostic already displayed is now dropped while the newly revealed lines are kept. By contrast a total-count line such as biome's `Found N errors.` is deliberately **retained**: output is truncated at 1000 characters by default, so the listed diagnostics are not necessarily all of them, and the count is the only remaining signal of what was cut
8. **Fail-Closed Security**: Block on parse errors, empty input, or missing/blank/incorrectly typed required agent fields. Required-field validation is deliberately scoped to the fields claw-hooks actually reads for a decision (event name, tool name/input, `tool_input.command` for Bash, the patch body for `apply_patch`, `stop_hook_active` for Stop). The scope is **per (tool, event) pair**, not per tool: a shell tool's `command` is the input to the dangerous-command check and is always required, but a file-editing tool's path is only read by the post-save hooks, so it is required on `PostToolUse` and not on `PreToolUse`. No filter looks at file input before execution — the built-in and custom filters are gated on `is_shell_tool()`, and the extension hook returns false immediately for any event other than `AfterFileEdit` — so requiring `file_path` on `PreToolUse` meant rejecting a write over a field that would never be consulted, and on Claude a `PreToolUse` rejection is an immediate hard block. Metadata that no filter consults (`cwd`, `model`, `transcript_path`, `turn_id`, `permission_mode`, `tool_use_id`, `tool_response`, …) is not required, because the agent specs present those as the fields you *usually* receive rather than a strict schema (the Codex docs' own `SessionEnd` example payload omits `model`), and requiring them would let a single omitted field fail every hook call closed and take the whole tool offline. Out-of-scope pass-through events are not validated at all — validating an event whose decision is discarded has no security upside and can produce a harmful spurious block (a Codex `UserPromptSubmit` deny rejects the user's prompt; a Codex `PostToolUse` deny *replaces the real tool output* with the hook message, so `PostToolUse` is only strictly validated for file-editing tools). Non-empty unknown/unsupported event names are still passed through as allow to keep claw-hooks within its intentional scope. **Only the events claw-hooks actually gates before execution fail closed**: `blocks_would_loop_or_be_ignored` is an allowlist keyed on the event name, and everything outside it (`PreToolUse` on Claude/Codex/Antigravity/Grok, `PermissionRequest` on Codex, `beforeShellExecution`/`preToolUse` on Cursor, `pre_run_command` on Windsurf) resolves to a neutral allow. Two independent reasons drive this. First, **Stop-family events**: on Claude/Codex a Stop `decision:"block"`, on Antigravity `decision:"continue"`, and on Cursor a `followup_message` all mean "do not stop, here is a new prompt" rather than "reject", so returning one for a malformed payload creates a self-sustaining loop (fail → continue → Stop re-fires → same failure) that no loop guard can break, since `stop_hook_active` / `loop_count` / the cross-process env flag all require a successful parse first. Stop is not a pre-execution gate — allowing the stop creates no new side effects, whereas auto-continuing induces further tool calls. Second, **events claw-hooks never inspects**: denying them has zero security upside and real cost — a Claude/Codex `UserPromptSubmit` deny erases the user's prompt, a Codex `PostToolUse` deny replaces the real tool output with the hook message, a Cursor `beforeReadFile` carries the full file body (so a large file trivially exceeds `MAX_INPUT_BYTES` and the read would be blocked by a tool that has no opinion on reads), and every Windsurf post-hook and every Grok event except `PreToolUse` cannot block at all, so a deny only injects a spurious error. The neutral response is the event-specific stop-allow shape + exit 0 (Antigravity uses `{"decision":"stop"}` for Stop and `{}` elsewhere, since only its Stop output requires `decision`; the other agents use `{}`). **When the event name cannot be determined at all, the guard stays fail-closed and blocks** — a truncated or oversized `PreToolUse` still denies. That guard needs the event name, so it must keep working when the payload cannot be parsed as JSON at all — otherwise the two cases where it is needed most (a truncated write, and an oversized payload, which `read_stdin_bounded` necessarily cuts at `MAX_INPUT_BYTES + 1` and therefore leaves as invalid JSON) fall through to a block and produce exactly the self-sustaining loop described above. `scan_event_name_in_malformed_input` therefore rescans the raw text for the event-name key when `serde_json` fails, and the oversized path passes the truncated input along instead of discarding it. The scan is deliberately narrow: it matches the quoted key exactly, takes the earliest match, reads only the first 4 KiB (agents place the event name near the front of the payload, while a giant `tool_input.command` body sits after it), and requires a closing quote — anything else returns `None` and the caller stays fail-closed. Misjudging in the permissive direction only ever allows a *stop*; `PreToolUse` payloads keep blocking on both truncation and oversize. Relatedly, the fail-closed writer picks its stream by exit code rather than by format: a Stop parse error resolves to the event-specific stop-allow response + exit 0, which is a decision document and belongs on stdout, whereas a genuine exit-2 block on Claude/Windsurf still writes its plain-text reason to stderr where those agents read it. **Configuration and startup failures are fail-closed too**: a TOML syntax error or failed validation used to propagate out of `main` as `exit 1` with empty stdout, which Codex/Antigravity read as "hook failed, ignore its decision" — one typo in `config.toml` silently disabled all command blocking. `HookService::emit_config_error` now reads the payload just far enough to identify the event and returns the agent's native deny shape (or the event-specific stop-allow response for Stop, per above), writing the diagnostic to stderr with a pointer to `claw-hooks check`. Logger initialization failure is non-fatal (warn, continue without logging) for the same reason, `HookService::emit_runtime_error` covers residual internal errors from `run`, and stdin I/O failure goes through the normal fail-closed path instead of `?`. Pathologically deep command nesting or oversized command input is also treated as a block candidate, avoiding recursion-based stack overflow that would otherwise crash and fail open. The pathological-input guard counts brace nesting (`{`/`}`) in addition to parentheses, and the AST walk enforces an explicit traversal-depth limit, so deeply nested command groups (`{ ...;}`) cannot overflow the stack and fail open even under small thread stacks (Windows/containers). Wrapper-chain expansion (`sudo sudo … rm`) is iterative with an explicit recursion bound rather than self-recursive, so a long wrapper chain that slips under the size limit cannot overflow the stack; chains exceeding the bound fail closed. The stdin reader is bounded (4 MiB) so an oversized or runaway hook payload is treated as fail-closed rather than allocating until the process is OOM-killed (which would otherwise drop the safeguard entirely). Stdin is read as raw bytes and decoded with lossy UTF-8 conversion (not `read_to_string`), so a stray invalid-UTF-8 byte cannot abort the process with `exit 1` and an empty stdout — a state Codex/Antigravity interpret as a failed hook (decision ignored = fail-open). Invalid bytes become U+FFFD and the input still flows through the normal parse/detect path: a now-unparseable payload fails closed (block), while a still-parseable command keeps its dangerous-command detection. Hook subprocess stdout/stderr pipes are drained to EOF but retain at most 4 MiB per stream, preventing a noisy formatter/linter from OOM-killing the hook before output normalization and agent-facing truncation. The allowlist in `blocks_would_loop_or_be_ignored` must stay in sync with the event mapping table: `parse_codex_input` maps the legacy alias `BeforeTool` onto the same `HookEvent::BeforeCommand` as `PreToolUse`, but the allowlist named only the latter, so an event declared to be a pre-execution gate resolved to a neutral allow whenever its payload failed to parse — a divergence between the two tables is silently a fail-open, which is why `BeforeTool` now appears in both (and in the branch that picks the recommended `hookSpecificOutput` deny shape). Finally, the **diagnostic text for a configuration or runtime error is withheld when stderr is the decision channel**. `emit_config_error` writes the config file's absolute path and the TOML parse error — which quotes the offending line — to stderr for the user's benefit, but Claude and Windsurf read stderr as the block reason on a non-zero exit, so both were handed straight to the agent; the diagnostic is now emitted only when `fail_closed_uses_stderr` is false, and the agent-facing text stays the fixed sentence that points at `claw-hooks check`.
9. **Process Group Isolation (Unix)**: Hook subprocesses are placed in their own process group via `setpgid`, so timeouts kill the whole tree (`killpg`) — preventing grandchild leaks like `sh -c 'sleep ...'` after the shell is signaled. If the direct child exits but a background grandchild still keeps stdout/stderr pipes open (for example `sh -c 'sleep 60 &'`), the pipe wait is also treated as a timeout and the process group is killed. After a normal child exit, the reader-thread join uses a short post-exit drain grace rather than reusing the original timeout deadline, so a command that completes right at the deadline still has its buffered output collected instead of being mis-reported as a timeout (which would otherwise return a spurious block to the agent for `report=true` stop hooks); a grandchild that keeps the pipe open past the grace still triggers the process-group kill.
10. **Debug Log Safety**: Debug logs store hook event summaries (event/tool/session/size) instead of raw hook input or raw parsed `ToolInput`, so tool command text, file contents, unknown event payloads, and agent messages are not persisted to disk. Per-agent parsed-input debug lines log byte counts and booleans (`command_bytes`, `file_path_bytes`, `has_cwd`) rather than raw command/file-path/cwd values, and the formatted hook output is logged as a decision + size summary; the full output body (which may include lint diagnostics quoting source lines) is available only via `--trace`, which writes to stderr and is not persisted. Extension-hook logs record the executable basename with arg-count / inline-template booleans and the resolved file path byte length instead of the expanded command line — executable directories, the actual file path and rendered command (which can contain user-directory hierarchies or source-quoting lint snippets) are kept off disk. Extension-hook failure logs and timeout messages use the same sanitized command label — but that label is **log-only**: the string handed to `run_with_timeout` is embedded verbatim in the timeout body, which reaches the agent as `additionalContext`, so it carries only the configured program name (matching the stop-hook path). Subagent notification logs record `type_bytes=<len>` rather than the agent name, in both the filter and the per-agent parsed-input lines: subagent names routinely contain internal project and team names, and `log_sanitizer` already suppresses the same field (its unit test pins that the name never appears in a log summary), so leaving it in an adjacent `debug!` defeated the rule. The hook-input summarizer recognises every agent's field naming — Grok's camelCase (`hookEventName` / `toolName` / `sessionId`) and Antigravity's `toolCall.name` (it has no event-name field at all) — because without them those two agents logged nothing but `event=<unknown> tool=- session_id=-`, which defeats the only purpose this log still has. Stop-hook queue/execution/completion logs likewise use only the executable basename and argument count; command arguments and executable directories are never persisted. Stop-hook output logging records only the byte size of stdout/stderr per hook; the full diagnostic body is still relayed to the agent via the block `reason`/`followup_message`, but it is never persisted to disk.

## Architecture Decisions

1. **Layered Architecture**: config → service → domain separation
2. **Filter Chain Pattern**: Priority-based extensible filter pipeline
3. **Adapter Pattern**: Convert agent-specific JSON to internal types
4. **tree-sitter for AST**: Accurate shell command parsing with robust fallback string parser for non-AST builds
5. **Fail-Closed Security**: Block commands when input parsing fails
6. **Intentional Scope Limits**: This tool is for command blocking, post-edit hooks, stop hooks, and subagent notifications. It must not expand into general lifecycle/prompt orchestration. `SessionStart`, `UserPromptSubmit`, and other unsupported lifecycle events are intentionally out of scope; adapters map them to the internal `HookEvent::Passthrough` marker, which must remain allow-by-design unless the project direction explicitly changes.
7. **Deny-Only Policy**: claw-hooks blocks; it never approves. An "allow" response must be the neutral empty object (`{}`) plus exit 0 — never an explicit approval token such as Claude's `permissionDecision: "allow"` or Cursor's `permission: "allow"`. Those tokens *skip the agent's own permission prompt*, so emitting them would turn a dangerous-command blocker into a blanket auto-approver for every command it does not block (installing claw-hooks with `matcher: "Bash"` would silently remove all Bash confirmations). The neutral response also keeps hook composition intact: agents that merge responses from several hook sources must not see claw-hooks approve an event it never inspected, since that can override another hook's deny. `HookEvent::Passthrough` must therefore serialize to `{}` for every format, and only `Decision::Block` may produce a decision token.
   - **Known deviation — Antigravity CLI**: its `PreToolUse` output schema marks `decision` as **Required** (`allow` / `deny` / `ask` / `force_ask` / `deny_unless_prior_grant`), so there is no documented neutral response; `{}` is undefined behavior. claw-hooks therefore still returns `{"decision":"allow"}` there, which does suppress Antigravity's own confirmation for commands it does not block. `"ask"` would preserve the prompt but force one on every command. Resolving this needs empirical confirmation of how Antigravity treats an omitted `decision`; do not change it on spec reading alone. Stop also requires `decision`; claw-hooks uses `{"decision":"stop"}` because only `"continue"` re-enters the loop and every other value permits stopping.

8. **Untrusted Project Config**: `.claw-hooks.toml` is merged from the current working directory, which means it can also be "a file inside a repository the agent just cloned". It is therefore treated as untrusted input: a project config may **strengthen** protection but never weaken it, and may never introduce a new command execution. `rm_block` / `kill_block` / `dd_block` merge as `global || project` (enabling is honored, disabling is ignored), `custom_filters` are appended rather than replacing the global set, and `stop_hooks` / `extension_hooks` are rejected outright because both would run arbitrary commands — at agent stop and on every file edit respectively. Message strings, `hook_timeout` and `output_max_length` stay overridable since none of them weaken a decision. Previously only `debug` / `log_path` / `nano_buddy` were global-only, which inverted the priority: the log destination was protected while the safety filters and command execution were not, so a single file in a cloned repository could switch off the blocking this tool exists to provide (verified: a directory containing `rm_block = false` allowed `rm -rf /`, and a `[[stop_hooks]]` entry there executed on the next Stop with no trust prompt). Every ignored entry is recorded as a warning, because silently dropping a setting hides *why* it has no effect. Validation follows the same boundary: `validate_project` checks only the fields that are actually applied (`hook_timeout`, `custom_filters`). Validating `stop_hooks` / `extension_hooks` there turned a value that is deliberately discarded into a hard error — a two-line `.claw-hooks.toml` with an empty `commands` array or an extension hook missing its `{file}` placeholder failed the whole config load, and the fail-closed path then denied every command in that directory, `ls` included. It also produced an odd asymmetry where a *correct* `stop_hooks` block was ignored with a warning while a *malformed* one took the agent offline. Global configuration is unaffected: `validate_values` still rejects both.

## Agent-Specific Notes

### Claude Code
- Primary development agent
- Uses CLAUDE.md (symlink to AGENTS.md) for instructions
- Format: `--format claude` (default)
- **matcher は `Bash|PowerShell` を使う**。公式仕様は「シェルコマンドを検査するフックは両方にマッチさせること」「Windows で Git Bash が無い環境では PowerShell ツールが自動で有効化され、Claude Code は Bash ツールを登録すらしない」「`Bash` だけにマッチするフックはそこでは一度も発火しない」と明記している。`PowerShell` の `tool_input` は `Bash` と同一形状（`command` / `description` / `timeout` / `run_in_background`）なので、claw-hooks は両方を `ToolInput::Bash` にマップして同じフィルターを通す
- PreToolUse Allow: `{}`（判定を返さない = 異議なし。公式仕様では `permissionDecision: "allow"` は「権限プロンプトをスキップする」意味で、exit 0 かつ判定なしが「通常の権限フローが適用される」を意味する。claw-hooks はブロックしなかったコマンドを自動承認しない — Architecture Decisions の Deny-Only Policy 参照）
- PreToolUse Block: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}`（トップレベル `decision`/`reason` は deprecated のため使用しない）
- PostToolUse Allow: `{}` (追加コンテキストがある場合は `hookSpecificOutput.additionalContext` を含む)
- PostToolUse Block: `{"decision":"block","reason":"..."}`
- 保存後フック（拡張子フック）の対象ツールは `Write` / `Edit` / `MultiEdit` / `NotebookEdit`。**`NotebookEdit` はファイルパスのキーが `file_path` ではなく `notebook_path`** なので、読み替えてから通常のファイル編集として扱う（読み替えないと `.ipynb` の formatter/linter が発火しない）。matcher には `Write|Edit|MultiEdit|NotebookEdit` を指定する。なお公式仕様は matcher の正規表現経路で「`Edit.*` は `Edit` と `NotebookEdit` の両方にマッチする」と述べており、完全一致させたい場合は `^Edit$` のようにアンカーを付けるよう案内している
- **`PreToolUse` ではファイル編集ツールの `tool_input` を必須にしない**。パスを読むのは保存後フック（`PostToolUse`）だけで、実行前にファイル入力を見るフィルターは 1 つも存在しない（組み込み・カスタムフィルターは `is_shell_tool()` でゲートされ、拡張子フックは `AfterFileEdit` 以外で即 false を返す）。読みもしないフィールドの欠落で deny を返すと、`matcher: "*"` で導入した環境や Claude 側がキー名を変えた場合に、全てのファイル書き込みがハードブロックされる。シェルツール（`Bash` / `PowerShell`）の `command` は判定入力そのものなので従来どおり必須で、`PostToolUse` のファイルパスも保存後フックの対象決定に使うため必須のまま
- Stop output: Allow = `{}`, Block = `{"decision":"block","reason":"..."}`
- Stop 入力の空白でない `agent_id` と `agent_type` が両方ある場合だけ委譲セッションと判定する。公式仕様は `agent_id` を「サブエージェント呼び出しの内側で発火したときだけ入る」、`agent_type` を「`--agent` 起動時またはサブエージェント内で入る」と定義しているため、この組で `StopSessionKind::Primary / Delegated` を判別し、`session_scope` によるフック選別と NanoBuddy 通知の抑止を行う。どちらかの欠落・空白・非文字列は Primary 扱い（フェイルセーフ方向）。インプロセスのサブエージェント（Agent tool）は Stop を発火せず `SubagentStop` のみ
- 通常の許可/ブロック判定は stdout JSON + exit code 0 で返す（構造化制御の推奨経路）。Claude は現在、exit 2 を含む全終了コードで有効な stdout JSON を読むが、exit 2 のブロック効果を JSON で上書きすることはできない
- Fail-closed errors: `PreToolUse` のパースエラーは exit code 2 + stderr にメッセージ本文をプレーンテキストで出力。JSON 判定を組み立てられないパース/起動エラーでも exit 2 自体がブロックを保証し、有効なブロック JSON が無い場合は stderr 本文が理由として使われる。**イベント名すら判別できない入力も同様にブロックする**
- ただし `PreToolUse` 以外のイベントのパースエラーは `{}` + exit 0 に倒す。`Stop` / `SubagentStop` での exit 2 / `decision:"block"` は「拒否」ではなく「停止させず reason を継続プロンプトにする」意味なので壊れたペイロードに返すと無限ループになり、`UserPromptSubmit` の exit 2 は**ユーザーのプロンプト自体を消去する**。いずれも claw-hooks が中身を検査していないイベントで、拒否を返してもセキュリティ上の利得はゼロで害だけが残る（Fail-Closed Security 参照）
- 未対応イベント（`StopFailure`, `PermissionRequest`, `PreCompact` 等）は allow でパススルー（Cursor / Codex と同じ挙動）
- **既知の制約 — `TeammateIdle` は意図的に未対応**。agent team の teammate が idle になる直前に発火する新イベントで、claw-hooks の「Stop 時の lint/通知」と目的は重なるが、入力に `stop_hook_active` / `loop_count` に相当する**ループカウンタが無い**（受け取るのは `teammate_name` と `team_name` だけ）。command hook の出力契約は「exit 2 + stderr = idle させず作業を継続させる」「`{"continue":false,"stopReason":"..."}` = teammate を完全停止させる」の二択で、前者は恒久的に失敗する lint で無限ループになり、後者は Stop hook の意味（失敗を伝えて直させる）を変えてしまう。有限な再試行上限を安全に持てるようになるまでは、未知イベントとして `{}` + exit 0（idle 許可）でパススルーする。したがって **teammate の idle 時には停止時 lint も通知も走らない**

### Cursor
- Refer to README.md for integration examples
- Use `--format cursor` when testing
- Input parsing uses `hook_event_name` field for event identification (not field-structure matching)
- Supported events: `preToolUse` for `Shell`/`Bash`, `beforeShellExecution`, `afterFileEdit`, `afterTabFileEdit`, `stop`, `subagentStart`, `subagentStop`
- Unsupported events (e.g., `afterShellExecution`, non-shell `preToolUse`, `postToolUse`) are passed through as allow
- Allow / パススルーはいずれも `{}` を返す。`permission: "allow"` は返さない。Cursor は複数ソースのフック応答をマージし優先度の高いソースが勝つ仕様なので、中身を検査していないイベント（`beforeReadFile` / `beforeMCPExecution` / `beforeTabFileRead` 等、いずれも `permission` が有効な判定フィールド）に allow を返すと他フックの deny を上書きし得る。`beforeSubmitPrompt` のように `permission` フィールドを持たないスキーマもある
- 判定はすべて stdout JSON + exit code 0 で返す（Block も exit 0）。Cursor の公式仕様は「exit 0 = 成功、JSON 出力を使う」「exit 2 = アクションをブロック（`permission: "deny"` と等価）」であり、deny JSON + exit 2 だとブロック自体は成立しても代替案の本文がエージェントに届かない。意図的なポリシー拒否は JSON 契約に統一し、判定系が壊れたパースエラーだけを exit code 契約（`error_exit_code`）に回す
- Block のメッセージは `user_message` と `agent_message` の**両方**に入れる。公式スキーマは `user_message` が「拒否時にユーザーへ表示する文言」、`agent_message` が「拒否時にエージェントへ返す文言」と定義しており、claw-hooks の主目的は代替コマンド（safe-rm 等）をエージェントに教えることなので、理由本文を `user_message` だけに入れるとエージェントは理由も代替手段も分からないまま同じコマンドを再試行する。フェイルクローズのエラー本文も同様に両方へ入れる
- `stop` / `subagentStop` の Output スキーマは公式に `{ followup_message?: string }` のみ（`permission` フィールドは存在しない）。Allow は `{}`、Block は `followup_message` に修正指示を入れて返す
- `stop` / `subagentStop` のパースエラーは `{}` + exit 0（停止許可）を返す。`followup_message` は「次のユーザーメッセージとして自動送信される」= 継続指示なので、壊れたペイロードで返すと同じ失敗を繰り返す（Fail-Closed Security 参照）
- `stop` の `loop_count`（stop hook 由来の自動フォローアップ発火回数、0 始まり）が 1 以上の場合は全 stop hook をスキップする。Cursor は `stop_hook_active` を持たないため、`loop_count` が無限フォローアップループ防止の役割を担う（Cursor 側の `loop_limit`(デフォルト5) に頼らず 1 回で止める）
- `preToolUse` はツール名ではなく `tool_input` の**形**で判定する。公式仕様はこのフックを「すべてのツール種別に発火する汎用フック」と定め、ツール名の列挙も "Values include `Shell`, `Read`, `Write`, ..." という非網羅の書き方をしている。名前の等値判定に頼ると、Cursor がシェル実行ツールを追加・改称した瞬間にコマンドブロックが丸ごと素通しになる（Grok と同じ理由・同じ方式）。`tool_input.command` が非空ならコマンド、無ければパススルー
- **ただし `preToolUse` の登録には matcher を付ける**。全ツール発火なので、matcher 無しだと `Write` のように巨大な `tool_input` を運ぶ呼び出しまで claw-hooks へ流れる。`MAX_INPUT_BYTES`(4 MiB) を超えた入力は切り詰められてパース不能になり、`preToolUse` は実行前ゲートなのでフェイルクローズドの deny を返す — claw-hooks が何の意見も持たないファイル書き込みを止めてしまう（`beforeReadFile` をフェイルクローズド対象から外したのと同じ理由）。公式仕様の matcher は**正規表現**（"A matcher is a regex string"）なので `"Shell|Bash|Terminal|Exec|Run|Command"` のように広く書けばよく、ツール名の等値判定に戻すわけではない。matcher の偽陽性は無害（届いた後は従来どおり `tool_input` の形で判定してパススルーする）で、偽陰性だけがコストだが、それはイベント単位でシェルを網羅する `beforeShellExecution` が二重に受ける。**先頭数 KiB を走査して `tool_input.command` の有無を確かめる案は採らない** — JSON オブジェクトのキー順に意味は無く、「走査範囲外にある」のと「存在しない」のを区別できないため、セキュリティ判断をシリアライザの偶然のキー順に依存させることになる（イベント名の走査フォールバックが成立するのは、エージェントがイベント名をペイロード先頭付近に置くという経験的規則性があるからで、`tool_input.command` にその根拠は無い）
- **既知の不確実性 — permission hook への `{}`**。公式仕様は「permission hook（`beforeShellExecution` / `beforeMCPExecution` / `beforeReadFile` / `beforeTabFileRead` / `subagentStart` / `preToolUse`）では invalid JSON またはフックのスキーマに合わない応答はアクションをブロックする」と述べ、`preToolUse` の出力表では `user_message` / `agent_message` / `updated_input` に "(optional)" が付く一方 **`permission` にだけ付いていない**。`permission` が必須なら、claw-hooks がブロックしなかった全コマンドが逆にブロックされる（主機能の反転）。`failClosed` の説明が「no output」と「invalid response」を別カテゴリとして扱っている点は `{}` を許す根拠に見えるが、`{}` は無出力ではなく**有効な JSON だが必須フィールドを欠く応答**なので、むしろ後者に入る読みと整合する。したがって現状の `{}` は「仕様で保証された中立応答」ではなく**未確認の前提**として扱い、README / AGENTS.md でも保証として書かないこと。検証は、他ソースのフックを混在させない隔離環境に**フックを 1 つだけ**登録し（`preToolUse` と `beforeShellExecution` を同時登録すると一方の結果が他方の deny に隠れる）、`{"permission":"allow"}` → `{"permission":"deny"}` → `{}` → 無出力 の順で実施する。`{}` の試験は **`failClosed: false`** で行う — 仕様は permission hook のスキーマ違反を「`failClosed` が false でもブロックする」と明記しているため、この設定ならスキーマ違反由来のブロックと `failClosed` 由来のブロックを切り分けられる。無出力 + exit 0 は代替にならない（`failClosed: true` では「no output」がフック失敗＝ブロック）。仮に `permission` 必須が確定した場合、「安全なコマンドを無確認で通す」「明示的 allow を返さない」「クラッシュ時も fail-closed」の 3 条件は同時に満たせず、Antigravity と同じ「既知の逸脱」として 2 番目を諦めるか、`beforeShellExecution` 単独 + `ask` 運用へ退避するかの二択になる（`preToolUse` の `ask` は仕様上「スキーマは受理するが現状 `preToolUse` では強制されない」= 実質 allow 相当なので使えない）
- **フックの作業ディレクトリは登録場所で変わる**。公式仕様では project hooks（`<project>/.cursor/hooks.json`）はプロジェクトルートで、user hooks（`~/.cursor/hooks.json`）は `~/.cursor/` で実行される。claw-hooks の stop hook 条件判定（`condition = { file_exists = "Cargo.toml" }` 等）・`.claw-hooks.toml` の探索・子プロセスの cwd はいずれもプロセスの cwd に依存するため、**プロジェクト単位の lint を使うなら project hooks に置く必要がある**。user hooks に置くと条件が永久に不成立になり、条件なしのフック（git 自動コミット等）は `~/.cursor/` で走る。README の設定例も project hooks を先に案内する
- **既知の制約 — 保存後 lint の診断は Cursor へ返せない**。`afterFileEdit` には公式に Output スキーマが存在せず（Input のみ定義）、formatter の書き換えはファイルに反映されるが linter の診断テキストを渡す先が無い。汎用の `postToolUse` には `additional_context` があるため経路自体は存在するが、`afterFileEdit` と二重に登録するとフォーマッタが 2 回走るため、どちらの経路に寄せるかを設定で排他にする必要がある。現状は `afterFileEdit` に統一し、診断は Stop hooks 経由で返す

### Windsurf
- Refer to README.md for integration examples
- Use `--format windsurf` when testing
- BeforeCommand (pre_run_command) Block: exit code 2 + stderr にメッセージ本文をプレーンテキストで出力（Windsurf は stdout/stderr を JSON 解析せず stderr を表示用テキストとして扱うため、`{"decision":...}` のような JSON ではなく本文のみを出す）。本文は他エージェントと同様に `normalize_lint_output` で ANSI/空白を正規化してから返す（ANSI エスケープが残ると Windsurf UI の表示が壊れるため）
- AfterFileEdit (post_write_code) で formatter/linter の診断があるとき: exit code 2 + stderr に診断本文を出力する。公式仕様は「exit 2 = Cascade エージェントが stderr のメッセージを見る」かつ「ブロックできるのは pre_* フックだけ」なので、事後フックでの exit 2 は**編集を巻き戻さずに診断だけを伝える**経路になる。`show_output: true` を設定していればユーザーにも同じ本文が表示される。Windsurf には `additionalContext` に相当する JSON フィールドが無いため、これが保存後 lint の結果をエージェントへ届ける唯一の手段である。診断が空のときは `{}` + exit 0 に倒す（編集のたびに無用なエラー表示を出さないため）
- Stop は `post_cascade_response` に対応する事後フックのためベストエフォート。stop hook が失敗しても `{}` を返し、エージェントにはブロックを返さない
- 未対応の `agent_action_name` は allow でパススルーする（全イベント対応が目的ではないため）
- フェイルクローズ（パースエラー/空入力）: ブロック可能な `pre_run_command` のみ exit code 2 + stderr にメッセージ本文をプレーンテキストで出力する。それ以外の `agent_action_name`（`post_cascade_response` / `post_run_command` / `post_read_code` 等）は `{}` + exit 0 に倒す。公式仕様上ブロックできるのは pre_* フックだけであり、事後フックに exit 2 を返してもエージェントに無用なエラーを注入するだけで判定にはならない

### Antigravity CLI
- 新規セットアップでは `--format agy` を使用する。設定は `hooks.json` (`.agents/hooks.json` または `~/.gemini/config/hooks.json` — Antigravity 公式が再利用する設定パス)
- Supports these hook events: `PreToolUse`, `PostToolUse`, `PreInvocation`, `PostInvocation`, `Stop`
- 公式入力スキーマは camelCase でイベント名フィールドを持たない。`toolCall`、Stop 固有フィールド、`stepIdx`、invocation 固有フィールドからイベントを判別する。後方互換の `hook_event_name` / `event` は空白でない文字列だけ受理する。`conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`, `modelName` 等も使用
- **`--event` でイベント名を明示指定できる**（`claw-hooks hook --format agy --event PostToolUse`）。公式スキーマでは PreToolUse と PostToolUse が**区別できない** — どちらも `toolCall`（`name` と `args`）と `stepIdx` を持ち、差は Optional な `error` だけである。一方 `hooks.json` はイベントごとに別エントリでコマンドを登録するため、呼び出し側は自分がどちらのイベントかを知っている。イベント名の決定順は `--event` → ペイロードの `hook_event_name` / `event`（旧版互換）→ 形状推定。推定に落ちた場合は **PreToolUse に倒す**（危険コマンドのブロックを維持するフェイルクローズド方向。逆に倒すと実行前のコマンドを素通しする）
- 必須フィールドは「claw-hooks が判定に使うもの」だけに絞る。公式仕様で **Required** マークが付くのは Stop の `fullyIdle` と出力の `decision` のみで、`stepIdx` / `executionNum` / `terminationReason` にはマークが無い。これらを必須にすると、PreToolUse では「即時ハードブロック」を意味する deny が全 `run_command` に出て、Stop では**エラー表示なしで全 stop hook（lint / commit / 通知）が黙って実行されなくなる**。Stop のパースエラーは `{"decision":"stop"}` + exit 0 に倒し、出力契約を満たしながら再投入ループを避ける。よって `stepIdx` / `executionNum` / `terminationReason` は任意扱いとし、`fullyIdle` のみ必須を維持する
- `toolCall.args` は `run_command` 分岐でしか読まないため、全ツール共通の必須項目にはしない。公式仕様は matcher `""` / `"*"`（全ツール一致）を認めており、引数を持たないツール（`list_permissions` 等）も列挙されている。共通で必須にするとスコープ外ツールに対して「即時ハードブロック」を意味する deny を返してしまう
- Use `--format agy` when testing
- PreToolUse Allow: `{"decision":"allow"}`（公式仕様で `decision` が必須のため、中立的な「判定なし」応答が存在しない。Deny-Only Policy の既知の逸脱として扱う — Architecture Decisions 参照）
- PreToolUse Block: `{"decision":"deny","reason":"..."}`（仕様上は `allow` / `deny` / `ask` / `force_ask` / `deny_unless_prior_grant` を取れるが、claw-hooks は allow / deny の二択で運用）
- PostToolUse output: `{}` 固定（公式仕様。事後フックでありブロック・追加コンテキスト伝達不可）
- PreInvocation / PostInvocation: claw-hooks のスコープ外（モデル呼び出し前後のオーケストレーション）なので allow でパススルー（`{}`）
- Stop output: Allow = `{"decision":"stop"}`, Block = `{"decision":"continue","reason":"..."}`（`continue` はエージェントを再投入し reason を system message として注入する。出力の `decision` は必須で、`continue` 以外なら停止する）
- 判定はすべて stdout JSON + exit code 0 で返す。フェイルクローズドのパースエラーは PreToolUse では `{"decision":"deny","reason":"..."}` を返す。Stop では `{"decision":"stop"}`（停止許可）を返す — `continue` は「停止させず再投入する」意味なので、壊れたペイロードに返すと Stop 再発火の無限ループになる（Fail-Closed Security 参照）
- PostToolUse は公式仕様上 `toolCall`（`name` と `args`）を含むため、**拡張子フック（保存後の auto-format / lint）は Antigravity でも成立する**。`write_to_file` / `replace_file_content` / `multi_replace_file_content` の `args.TargetFile` から編集対象を復元して実行する。ただし出力は仕様どおり `{}` 固定なので、formatter/linter の**実行はできるが結果をエージェントへ返せない**。診断を伝えたい場合は従来どおり Stop hooks で lint/typecheck を回し、Block を `"decision":"continue"` で再投入する。`hooks.json` の PostToolUse エントリには `--event PostToolUse` を付けること（付けないと形状推定が PreToolUse に倒れる）
- PostToolUse の `run_command`（実行済みコマンド）は deny を返さずパススルーする。実行後にブロックしても意味が無く、公式仕様も出力は `{}` 固定と定めている。**これは `--event PostToolUse` を指定したときの話**で、指定が無いと形状推定が PreToolUse に倒れて実行済みコマンドにも deny が出る（`hooks.json` の PostToolUse エントリには必ず `--event` を付けること）
- **既知の制約**: Antigravity の Stop には `stop_hook_active`（Claude/Codex）や `loop_count`（Cursor）に相当する入力が無い。`executionNum` は公式例で通常の初回停止が `"executionNum": 1` となっており「実行試行の連番」でしかないため、これをループカウンタとして扱うと初回 Stop から全フックが抑止されて機能が壊れる。したがって Antigravity では、恒久的に失敗する stop hook が `"decision":"continue"` を返し続けるループを claw-hooks 側では遮断できない（プロセス間の環境変数フラグは子プロセスにしか伝播しない）。report=true の stop hook には自己完結する終了条件を持たせること
- `manage_task` の `Action: "send_input"` は、`Input` が実行中プロセスの標準入力へ送られるためコマンド本文として検査する。`run_command` を `RunPersistent: true` で起動して永続シェルを作れば、以降は `send_input` でコマンドを流し込めて `CommandLine` を一度も通らないため、ここを見ないと rm / kill / dd フィルタが完全に迂回される。`list` / `status` / `kill` はエージェント自身のタスク管理操作（シェルの `kill` コマンドとは別物）なので対象外。`hooks.json` の matcher は `run_command|manage_task` にすること
- run_command（args.CommandLine）以外のツール（`write_to_file` / `replace_file_content` / `multi_replace_file_content` / `view_file` / `list_dir` / `find_by_name` / `grep_search` / `invoke_subagent` / ...）は claw-hooks のコマンドブロックの対象外として PreToolUse でパススルー（`{"decision":"allow"}`）。ここで内部の `HookEvent::Passthrough` に落としてはいけない — Passthrough は全フォーマット共通で `{}` を返すため、`decision` が必須の Antigravity PreToolUse では必須フィールドを欠いた未定義の応答になる（matcher を `""` / `"*"` にすると run_command 以外の全ツールでこれが起きる）。`HookEvent::BeforeCommand` + `ToolInput::Other` にマップすれば、組み込み/カスタムフィルターはどちらも `is_shell_tool()`（Bash / PowerShell）しか見ないため無害に Allow へ落ち、`{"decision":"allow"}` が返る（Codex が未知のツール名を `ToolInput::Other` で素通しするのと同じ手法）
- 未対応イベント（`SomeNewEvent` 等）は allow でパススルー（他エージェントと同じ）
- Official docs: https://antigravity.google/docs/customizations/hooks

### Codex CLI
- Supports these hook events: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, `Stop`, `Interrupt`
- Use `--format codex` when testing
- Allow output: `{}` (empty JSON, exit 0)
- PreToolUse Block output: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}`（公式ドキュメントの主形式。legacy の `{"decision":"block"}` も受理されるが使用しない）
- PostToolUse / Stop Block output: `{"decision":"block","reason":"..."}`（これらのイベントではこれが正式形式。Stop では reason が継続プロンプトになる）
- PermissionRequest Block output: `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"deny","message":"..."}}}`
- 入力検証は「claw-hooks が判定に使うフィールド」だけに絞る: イベント名、`tool_name` / `tool_input`（Bash は `tool_input.command`、`apply_patch` は patch 本文）、Stop の `stop_hook_active`。`session_id` はログ・通知の相関用なので存在すれば取り出すだけ、`cwd` / `model` / `transcript_path` / `turn_id` / `permission_mode` / `tool_use_id` / `tool_response` は判定に使わないため検証しない。公式の共通フィールド表は「通常使うフィールド」の一覧であって厳密なスキーマではなく（仕様中の SessionEnd 実例ペイロードには `model` が無い）、これらを必須にするとフィールド 1 つの省略で全イベントがフェイルクローズドに倒れて claw-hooks 全体が停止する
- スコープ外のパススルーイベントはフィールド検証を一切行わない。判定が破棄されるイベントを検証してフェイルクローズドにするとセキュリティ上の利得ゼロで害だけがある（`UserPromptSubmit` の `decision:"block"` はユーザーのプロンプト自体の拒否が正式形式）
- `PostToolUse` はファイル編集系ツール（`apply_patch` / `Write` / `Edit` / `MultiEdit`）だけ厳密検証する。Codex の `PostToolUse` では `decision:"block"` が「実際のツール出力をフックのメッセージで置き換える」動作になるため、保存後フックが使わない Bash 等の `tool_input` を検証してフェイルクローズドすると、モデルが本来のコマンド出力を失う
- `tool_input` の存在チェックは**ツール種別の判定より後**に行うこと。公式仕様では MCP ツール（`mcp__*`）や `update_plan` のような関数ツールも同じフック経路を通り、引数を持たないツールは `tool_input` を送らない。取得を先に必須化すると、上のファイル編集系限定の逃がし分岐に到達する前に落ちてしまい、`PostToolUse` では本来のツール出力が破棄され、`PreToolUse` では引数なしツールに誤 deny が出る。必須にするのは claw-hooks が実際に中身を見るツール（`Bash` / `PowerShell` / `Write` / `Edit` / `MultiEdit` / `apply_patch`）だけで、それ以外は欠落を許容して `ToolInput::Other` で素通しする
- PermissionRequest の parse error も PermissionRequest 専用 deny schema で返す
- PreToolUse の parse error も PreToolUse 推奨形式（`hookSpecificOutput.permissionDecision="deny"`）で返す。イベント名が判別できない入力は legacy block 形式（全イベント共通で受理される）にフォールバック
- PostToolUse の追加コンテキストは `hookSpecificOutput.additionalContext` で返す
- Codex `SessionStart` / `SessionEnd` / `UserPromptSubmit` / `PreCompact` / `PostCompact` / `Interrupt` は claw-hooks のスコープ外として中立応答 `{}` でパススルー
- Codex `PreToolUse` / `PermissionRequest` / `PostToolUse` は `Bash` と `apply_patch` を受け取る。`apply_patch` は `MultiEdit` にマップし、patch コマンドから変更ファイルパスを抽出する。旧版互換のエイリアスは `shell` / `run_command` / `execute` → `Bash` のみで、未知のツール名は写像せずそのまま渡す（`Write` に寄せると `file_path` が必須化され、引数キーが `path` / `filename` 等の関数ツールに PreToolUse の誤 deny が発生する。未知名は `ToolInput::Other` になり、組み込みフィルターは `tool_name == "Bash"` しか見ないので無害に素通しされる）
- イベント名の旧版エイリアス（`BeforeTool` → `PreToolUse`、`AfterTool` → `PostToolUse`）を受理するなら、**イベント写像表とフェイルクローズドの許可リストの両方に載せる**こと。片方だけに書くと、実行前ゲートとして扱うと宣言したイベントがパースエラー時に中立 allow へ倒れる（`BeforeTool` が実際にこの状態で、`tool_input` を欠くペイロードが `{}` + exit 0 で素通りしていた）。`format_error_for_input` の PreToolUse 分岐にも同じ名前を並べないと、deny 自体は成立しても legacy の `{"decision":"block"}` 形式になる
- Codex `SubagentStart` / `SubagentStop` は内部通知イベントとして扱う。NanoBuddy 用に `ToolInput::Subagent` へマップするが、README.md / README.ja.md には記載しない
- **既知の制約 — `write_stdin` は PreToolUse を再発火しない**。公式仕様は「`write_stdin` は既存の unified-exec セッションへの転送であり、すでに `PreToolUse` を通過したコマンドへ入力を送る/ポーリングする際に `PreToolUse` を再実行しない」「一部の特殊なツール経路は既定のフック経路をオプトアウトできる。ツールフックは有用なガードレールであって完全な強制境界ではないものとして扱うこと」と明記している。したがって `exec_command` で対話シェルを起動 → `write_stdin` でコマンドを流す経路は claw-hooks では塞げない（上流の設計上の制約）
- Official docs: https://learn.chatgpt.com/docs/hooks

### Grok CLI
- Use `--format grok` when testing。設定は JSON で個人が `~/.grok/hooks/*.json`、プロジェクトが `<project>/.grok/hooks/*.json`。Grok は Claude Code (`.claude/settings.json`) と Cursor (`.cursor/hooks.json`) のフック設定も読み込む。プロジェクトフックは `/hooks-trust` または `--trust` による信頼付与が必要
- 公式入力スキーマは camelCase: 共通で `hookEventName` / `sessionId` / `cwd` / `workspaceRoot`、ツール系イベントで `toolName` / `toolInput`。後方互換として snake_case（`hook_event_name` / `session_id` / `tool_name` / `tool_input`）も受理する
- Supported events: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionDenied`, `Stop`, `StopFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `PreCompact`, `PostCompact`
- **`PreToolUse` がブロック可能な唯一のイベント**。claw-hooks が扱うのは `PreToolUse`（コマンドブロック）/ `PostToolUse`（保存後フック）/ `Stop`（lint・通知）/ `SubagentStart` / `SubagentStop`（通知）で、それ以外はパススルー
- PreToolUse Allow: `{}` + exit 0（公式に文書化されている `decision` 値は `"deny"` のみなので、未文書の `"allow"` を返して「不正出力＝フェイルオープン」扱いになるのを避ける）
- PreToolUse Block: `{"decision":"deny","reason":"..."}` + **exit code 2**。公式仕様は「exit 0 は許可、exit 2 は拒否」かつ「それ以外（タイムアウト・クラッシュ・不正出力）はフェイルオープン」なので、Block で exit 0 を返すと実装側が終了コードを優先した場合に許可へ倒れ得る。exit 2 は明示的に拒否と規定されているため、stdout の deny JSON と exit 2 を両方出してどちらの解釈でもブロックを成立させる
- PreToolUse 以外は「stdout は無視され、成功なら exit 0」の事後フックなので、内部判定が Block でも `{}` + exit 0 を返す。したがって Grok では Stop フックの lint 失敗をエージェントへ伝えられない（Windsurf の `post_cascade_response` と同じ制約）
- フェイルクローズは exit code 2 を使う（exit 1 等はフェイルオープン扱いになるため）。`format_uses_stderr_for_errors()` は false で、判定は stdout の JSON で返す
- ツール名ではなく `toolInput` の形で判定する。Grok は「Claude のツール名（`Bash` / `Read` / `Edit` 等）を自前のツール名へ自動マッピングする」と明記しているが、マッピング後の実際のツール名は公開仕様に列挙されていない。ツール名の文字列一致に頼ると想定外の名前のシェル実行ツールが素通りしてブロックを回避できるため、`toolInput.command` を持てばコマンド（`Bash`）、`toolInput.file_path` / `filePath` を持てばファイル編集（`Write`）として扱い、どちらも無ければパススルーする
- `PreToolUse` のファイル編集と `PostToolUse` のコマンドはいずれもパススルー（編集前は責務外、実行後のコマンドはブロック不可で保存後フックの対象にもならない）
- `toolName` / `toolInput` は必須にしない。内部イベントは `toolInput` の形だけで決まり、ツール名は判定に使わない（ログとパススルー時の表示のみ）。必須化すると、それらを送らない形が 1 つでもあった時点で無関係なコマンドまで deny になる（Grok の `PreToolUse` は claw-hooks で唯一のハードブロック経路）。引数を持たないツールは `toolInput` をキーごと送らないため、欠落は空オブジェクト扱いにして「command もファイルパスも無い＝管轄外」へ落とす
- ファイル編集の判定では `file_path` / `filePath` に加えて `notebook_path` / `notebookPath` も見る。Grok は Claude のツール名を自前のツール名へ自動マッピングするため `.ipynb` 編集のキーも Claude 互換で届く。拾わないとノートブック編集の formatter/linter が無言でスキップされる（Claude 経路で同型のバグを直したのと同じ理由）
- Grok には `stop_hook_active` / `loop_count` に相当する入力が無いため、無限ループ防止はプロセス間の環境変数フラグ層が担う。API エラー終了は別イベント `StopFailure` に分かれており `Stop` には来ない
- Grok `SubagentStart` / `SubagentStop` は内部通知イベントとして扱う。README.md / README.ja.md には記載しない

## Configuration

Default: `~/.config/claw-hooks/config.toml`

`log_path` accepts a leading `~` and expands it to the home directory. TOML has no shell-style expansion of its own, so an unexpanded `~/…` is simply a relative path resolved against the hook process's cwd — the repository the agent is working in — and the generated default config offers exactly that form as a commented example. Without expansion it creates a literal `~` directory inside the user's project, and a `git` auto-commit stop hook then sweeps the hook logs into their repository. `~user` is left untouched because the target user's home cannot be resolved.

See README.md for full configuration reference.
